# Bit-Manipulation Extensions

VeeR EH1 implements the ratified RISC-V bit-manipulation extensions Zba (address generation), Zbb (basic bit manipulation) and Zbs (single-bit instructions), RV32 subset.
Together they form the B extension.
Each of them can be removed with a build argument (see [Build Arguments](#build-arguments)).

## Instructions

| Extension | Instructions | Count |
|---|---|---|
| Zba | `sh1add`, `sh2add`, `sh3add` | 3 |
| Zbb | `andn`, `orn`, `xnor`, `clz`, `ctz`, `cpop`, `min`, `minu`, `max`, `maxu`, `sext.b`, `sext.h`, `zext.h`, `rol`, `ror`, `rori`, `orc.b`, `rev8` | 18 |
| Zbs | `bclr`, `bclri`, `bext`, `bexti`, `binv`, `binvi`, `bset`, `bseti` | 8 |

The instructions of Zbc (carry-less multiply) and of the scalar cryptography extensions Zbkb, Zbkc and Zbkx are not implemented, nor are the RV64-only encodings; they take an illegal-instruction exception.

## Execution

All of the instructions are ALU instructions with a latency of one cycle.
Like the other ALU instructions, they can issue in either of the two pipes (i0, i1), two per cycle, and execute in the primary ALUs (EX1) or, when an operand comes from a load or a multiply that has not completed yet, in the secondary ALUs (EX4).
Their results are forwarded like any other ALU result, including to stores and to branches.

## Discovery

When all three extensions are configured, `misa` bit 1 (B) is set and `misa` reads 0x4000_1106; otherwise it reads 0x4000_1104.
The build also defines `RV_BITMANIP_ZBA`, `RV_BITMANIP_ZBB` and `RV_BITMANIP_ZBS` in `defines.h` and `common_defines.vh` for each configured extension.

## Build Arguments

- Zba (RV\_BITMANIP\_ZBA): 0, 1 (*default 1*)
- Zbb (RV\_BITMANIP\_ZBB): 0, 1 (*default 1*)
- Zbs (RV\_BITMANIP\_ZBS): 0, 1 (*default 1*)

For example, `veer.config -set=bitmanip_zbb=0` builds a core without Zbb.
A removed extension's instructions take an illegal-instruction exception and its datapath control signals are tied off, so synthesis removes the corresponding logic.

## Compiling for the Extensions

With GCC or LLVM, add the extensions to the architecture string, for example `-march=rv32imc_zba_zbb_zbs_zicsr_zifencei`.
Toolchains that know the B extension also accept `-march=rv32imcb_zicsr_zifencei`.

## Implementation Notes

The extensions are decoded by the generated decoder (`design/dec/decode`) and executed in `exu_alu_ctl`, mostly by reusing the existing ALU units:

| Instructions | Unit |
|---|---|
| `sh1add`, `sh2add`, `sh3add` | Adder. *rs1* is shifted by 1, 2 or 3 on its way into the ALU operand register, so the adder and the branch-resolution path that shares it get no extra logic. |
| `andn`, `orn`, `xnor` | Logic unit with the second operand inverted |
| `bset`, `bclr`, `binv` (and immediate forms) | Logic unit (or, and-not, xor) with the second operand replaced by the one-hot mask `1 << rs2[4:0]` |
| `rol`, `ror`, `rori` | Shifter in rotate mode. The three shifters of earlier releases (left, right logical, right arithmetic) are replaced by one funnel shifter that performs all five shift and rotate operations. |
| `bext`, `bexti` | Shifter (logical right shift), bit 0 of the result |
| `min`, `minu`, `max`, `maxu` | Adder computes *rs1* − *rs2*; the less-than result selects *rs1* or *rs2* |
| `clz`, `ctz` | One log-depth leading-zero counter; `ctz` feeds it the bit-reversed operand |
| `cpop` | Adder tree |
| `sext.b`, `sext.h`, `zext.h`, `orc.b`, `rev8` | Wiring and byte-wise OR |

The single-operand Zbb instructions (`clz` through `rev8` in the last three rows) share one control bit in the pipeline.
The decoder treats their instruction bits [31:20] as an immediate, which already travels with the instruction as the second operand, and the ALU selects the operation from it.

The signed and unsigned less-than result used by branches, `slt` and `min`/`max` is computed from the adder's carry-out and the operand sign bits, which shortens the branch-resolution path compared with deriving it from the sum and an overflow term.

## Tests

`testbench/tests/bitmanip` and `testbench/tests/bitmanip_random` are self-checking tests generated by `tools/gen_bitmanip_tests.py`:

- `bitmanip` checks every instruction against edge-case and random operands supplied through immediates, DCCM loads and multiplies (secondary ALUs) and back-to-back results, in both pipes.
  It also checks that unimplemented neighboring encodings, and the instructions of any extension configured out, take an illegal-instruction exception with the instruction in `mtval`.
- `bitmanip_random` executes a random stream of bit-manipulation, ALU, load, store, multiply and branch instructions and then checks all registers and the data memory.

The script can generate the same tests as Linux user-mode programs (`--target qemu`), which allows cross-checking its reference model against QEMU.
